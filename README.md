# 公交刷卡票价核验台（FastAPI + SQLite + 原生前端）

录入站点分区、票价矩阵、换乘抵扣额、每日封顶额及刷卡记录，系统按卡号配对进出站、
按运营日与换乘规则计算票价，并在数据异常时给出**可定位**的错误且**不生成部分账单**。
另支持**规则试算对比**：输入一组不保存的草案参数，对同一批记录分别按当前配置与草案
计费，逐程与整批对比金额变化；**配对修复预览**：针对缺失进站 / 缺失出站 /
连续同向刷卡，用全局最小编辑搜索生成可完整配对的修复方案（只读，不保存任何改动）；
以及**票价矩阵路径审计**：以分区为节点、已配置的有向票价为边，对实际行程分区对
计算最低成本路径，缺直达票价时给出建议票价与完整路径、直达票价偏贵时标出差额
（只读，不修改矩阵或账单）。

- 后端：FastAPI（Python 3.11）
- 数据库：SQLite（标准库 `sqlite3`，金额以**整数分**存储）
- 前端：原生 HTML / CSS / JavaScript，无框架、无构建步骤
- 部署：Dockerfile + docker-compose，数据持久化到命名卷

## 快速开始

单条启动命令（构建并后台启动）：

```bash
docker compose up -d --build
```

启动后访问 **http://localhost:8000**（端口 **8000**，交互式 API 文档在
http://localhost:8000/docs）。

停止与清理：

```bash
docker compose down          # 停止（保留数据卷）
docker compose down -v       # 停止并删除数据
```

本地裸机运行（不使用 Docker）：

```bash
pip install -r requirements.txt
DB_PATH=./bus.db uvicorn app.main:app --host 0.0.0.0 --port 8000
# 访问地址同样是 http://localhost:8000 （端口 8000）
```

## 业务规则

1. **进出站配对**：刷卡记录按卡号分组、时间升序排列，必须从进站开始且进出成对。
   - 一条进站没有后续出站 → `MISSING_EXIT`（缺失出站）
   - 起始是出站，或出站前没有进站 → `MISSING_ENTRY`（缺失进站）
2. **运营日归属**：行程按**进站时刻**归属运营日，默认以 **04:00** 为分界。
   例如 `2026-09-19 03:20` 的进站属于 `2026-09-18` 运营日。分界时刻可在页面配置。
3. **换乘抵扣**：同一卡号「前次出站 → 下次进站」间隔 **≤ 90 分钟**（可配置）时，
   先抵扣换乘优惠额（默认 1 元，跨运营日的 90 分钟内换乘同样适用）。
   - 抵扣额不超过该程基础票价，最小为 0。
4. **当日封顶**：抵扣之后再按「卡号 + 运营日」应用封顶（默认 10 元/日）。
   - 实扣 = max(0, min(基础票价 − 换乘抵扣, 封顶额 − 当日已累计))
   - 累计额按实扣逐程累加；封顶后后续行程实扣 0。
5. **原子核验**：只要存在任何记录级错误（缺失出站/进站、时间逆序、重复刷卡、
   未知站点、票价矩阵缺项），整批核验失败，**不写入任何账单**（无部分账单）。
   旧账单同时清空，避免过期数据被误读。
6. **重复刷卡 / 时间逆序**：
   - 同卡两条记录时刻完全相同 → `DUPLICATE_SWIPE`（重复刷卡）
   - 同卡出站早于进站、或排序后存在逆序 → `TIME_REVERSED`（时间逆序）
   - 错误信息同时给出卡号、时刻、站点与**原始文本行号**。

账单字段：卡号、卡内序号、运营日、进站/出站时刻、进出站点与分区、
**基础票价、优惠额、优惠来源说明、实扣额、当日累计额（/封顶额）**。

7. **规则试算对比**：在「2. 规则试算对比」区填入一组**不会保存**的草案参数
   （换乘时限、抵扣额、每日封顶、运营日分界），调用试算接口对**当前已保存的同一批
   刷卡记录**分别按当前配置与草案配置计费。
   - 试算与正式核验**完全复用同一套解析、配对与计价规则**，不修改任何配置、
     不写入或清空账单（纯只读）。
   - 任一方案存在错误时（草案参数非法 `CONFIG_BAD`，或数据错误如缺出站、未知站点、
     缺票价等），接口返回 422，`current` / `draft` 两个分块各自携带该方案的
     **原有定位错误**（错误码、行号、卡号、时刻、站点与 `/api/verify` 一致）。
   - 两边均成功时，按**卡号 + 卡内序号**对齐行程，逐程展示运营日（发生归属变化时
     高亮）、当前/草案优惠、当前/草案实扣及差额，并给出每张卡与全批次的实扣、
     优惠合计及差额。差额口径统一为「草案 − 当前」：实扣差额为正表示多付（红），
     为负表示少付（绿）。
8. **配对修复预览**：在「6. 配对修复预览」区对已保存记录一键生成修复方案。
   - 只处理配对结构问题：缺失进站、缺失出站、连续同向刷卡（即核验时的
     `MISSING_ENTRY` / `MISSING_EXIT`）；未知站点、缺票价、时间逆序、重复刷卡等
     非配对错误**按原错误返回**，不生成方案。
   - 记录按卡号分组、卡内按时间升序，做**全局最小编辑搜索**；允许的编辑只有
     **翻转进/出方向**与**删除记录**（各计 1 次编辑），原始时刻、站点、卡号
     一律不改写。修复后的方向序列必然从进站开始严格交替（可完整配对）。
   - 存在多个同成本方案时按**稳定顺序**最多返回 **5** 个，并标明最小编辑数与
     未展示的方案数量；系统**不擅自选定**任何方案。
   - 预览**全程只读**：不保存记录、不写入也不清空账单。页面逐条展示变更、
     修复后的完整记录文本，并提供复制按钮，是否采纳由人工决定。
9. **票价矩阵路径审计**：在「8. 票价矩阵路径审计」区对已保存数据一键审计。
   以分区为节点、已配置的有向票价为边，对已保存刷卡记录配对出的**实际行程
   分区对**计算最低成本路径（整数分 Dijkstra，相同总价按分区序列字典序
   稳定选路，零价边与非对称方向按有向图语义处理）：
   - 缺直达票价但存在可达路径：给出**建议票价**（= 最低成本路径总价）、
     **完整路径**（逐段分区与单价）、**建议补录行**（可复制），以及
     **受影响卡号与原始行号**；
   - 缺直达票价且不可达：保留原 `MISSING_FARE` 定位错误（卡号、行号、
     时刻、站点与 `/api/verify` 一致）；
   - 已有直达票价高于间接路径：标出**差额**（直达 − 间接最低）与
     最低成本路径；
   - 同区行程（如 1→1）按「至少经过一条边」的闭合路径计算，不会把
     「原地不动」当成 0 元路径；
   - 除 `MISSING_FARE` 外的数据错误（未知站点、缺出站、时间逆序等）：
     按 `/api/verify` 的原有定位错误返回，不生成审计结果；
   - 审计**全程只读**：不修改票价矩阵、不写入也不清空账单。

## 录入格式

页面上每个区块都是「每行一条」的纯文本，分隔符支持逗号、制表符、分号、空白与全角逗号；
空行与 `#` 开头的注释行会被忽略。

| 区块 | 每行格式 | 示例 |
|---|---|---|
| 站点分区 | `站点名, 分区号` | `科技园, 1` |
| 票价矩阵 | `起始分区, 到达分区, 票价` | `1, 2, 3.00`（按方向精确匹配） |
| 刷卡记录 | `卡号, 时刻, 站点, 进/出` | `A001, 2026-09-18 08:00:00, 科技园, 进` |

- 刷卡方向：`IN` / `进` / `进站` 或 `OUT` / `出` / `出站`。
- 时刻格式：`YYYY-MM-DD HH:MM[:SS]`、`YYYY/MM/DD HH:MM`、`YYYY-MM-DDTHH:MM:SS`、
  或月日格式 `MM-DD HH:MM`（自动补当前年份）。
- 站点名与分区、矩阵项均不可重复定义；刷卡记录中的重复刷卡是业务校验，
  在「运行核验」时报告。

### 内置演示数据

点击页面右上角 **「载入演示数据」**，会写入 3 个站点、3×3 票价矩阵与两张卡的记录：

- 卡 A 在同一运营日内 4 次出行：演示换乘抵扣（间隔 ≤90 分钟）与当日封顶（累计到 10 元）；
- 卡 B 在 `03:20` 进站：演示 04:00 运营日归属。

可故意制造以下错误观察定位效果（核验后整批不出账单）：

```text
# 删除某卡最后一条出站        -> MISSING_EXIT
# 让同一卡两条记录时刻相同      -> DUPLICATE_SWIPE
# 让出站时刻早于进站时刻        -> TIME_REVERSED
# 录入未定义的站点名           -> UNKNOWN_STATION
# 删除矩阵中的某个分区对       -> MISSING_FARE
```

删除实际行程用到的票价行（如 `2, 3, 3.00`）后，可到「8. 票价矩阵路径审计」
观察建议补录行（本例建议 `2, 3, 7.00`，路径 2→1→3）；把某条直达票价改高
（如 `2, 3, 9.00`）再审计，可观察「直达票价高于间接路径」的差额标注。

## HTTP API

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/api/config` | 读取规则参数 |
| PUT | `/api/config` | 更新参数（使旧账单失效） |
| GET/PUT | `/api/stations` | 读取 / 整批替换站点分区，PUT body：`{"text": "..."}` |
| GET/PUT | `/api/fares` | 读取 / 整批替换票价矩阵 |
| GET/PUT | `/api/records` | 读取 / 整批替换刷卡记录 |
| POST | `/api/verify` | 执行核验；成功写入账单，失败返回 422 与错误数组 |
| POST | `/api/trial-compare` | 规则试算对比（只读，不改配置/不写账单） |
| POST | `/api/repair-preview` | 配对修复预览（只读，不改记录/不写账单） |
| POST | `/api/fare-path-audit` | 票价矩阵路径审计（只读，不改矩阵/不写账单） |
| GET | `/api/bills` | 读取最近一次成功核验的账单 |
| GET | `/api/health` | 健康检查 |

### `/api/trial-compare` 规则试算对比

请求体为**草案参数**（均必填；数值合法性由核心层校验，非法时返回 422 +
`CONFIG_BAD`，而不是请求体校验错误）：

```json
{
  "transfer_minutes": 120,
  "transfer_discount": 2.00,
  "daily_cap": 15.00,
  "day_split_hour": 5
}
```

两方案均成功时返回 `200`：

```json

  "rows": [
    {
      "card": "A001", "seq": 2,
      "entry_time": "2026-09-18 09:10:00", "exit_time": "2026-09-18 09:50:00",
      "entry_station": "中心公园", "exit_station": "大学城",
      "from_zone": 2, "to_zone": 3, "base_fare": 3.0,
      "current_operating_day": "2026-09-18", "draft_operating_day": "2026-09-18",
      "day_changed": false,
      "current_discount": 1.0, "draft_discount": 2.0, "discount_diff": 1.0,
      "current_charge": 2.0, "draft_charge": 1.0, "charge_diff": -1.0,
      "draft_discount_source": "换乘优惠（距上次出站 45 分钟，≤120 分钟，抵扣 2.00 元）",
```

试算为只读操作：成功与失败都不会改动 `meta` 中的规则参数，也不会写入或清空
`trip_bill`。

### `/api/repair-preview` 配对修复预览

无请求体。针对**已保存**的刷卡记录做全局最小编辑搜索，返回可完整配对的修复方案。
全程只读：不保存记录、不写入或清空账单。

记录已配对时（无需修复）：

```json
{ "ok": true, "min_edits": 0, "total_plans": 0,
  "shown_plans": 0, "hidden_plans": 0, "plans": [] }
```

存在配对问题时返回 `200` 与最小编辑方案（按稳定顺序最多 5 个）：

```json
{
  "ok": true,
  "min_edits": 2,
  "total_plans": 3,
  "shown_plans": 3,
  "hidden_plans": 0,
  "plans": [
    {
      "edit_count": 2,
      "change_count": 2,
      "kept_count": 4,
      "trip_count": 2,
      "changes": [
        { "op": "flip", "card": "A001", "time": "2026-09-18 09:00:00",
          "station": "中心公园", "line": 3,
          "from_action": "OUT", "to_action": "IN",
          "detail": "翻转方向：A001 2026-09-18 09:00:00 @ 中心公园（OUT → IN）" },
        { "op": "delete", "card": "A001", "time": "2026-09-18 12:00:00",
          "station": "科技园", "line": 6,
          "from_action": "IN", "to_action": null,
          "detail": "删除记录：A001 2026-09-18 12:00:00 @ 科技园（原方向 IN）" }
      ],
      "fixed_text": "A001, 2026-09-18 08:00:00, 科技园, 进\n..."
    }
  ]
}
```

- `min_edits`：全局最小编辑数（各卡最小编辑之和；翻转 / 删除各计 1 次）。
- `total_plans` / `shown_plans` / `hidden_plans`：同成本方案总数、本次展示条数
  （≤5）与未展示条数；接口不替调用方选定方案。
- `changes[].op`：`flip`（翻转进/出方向）或 `delete`（删除记录）；
  `line` 为原始文本行号。修复只改方向或删记录，时刻与站点保持原值。
- `fixed_text`：修复后的完整记录文本（按卡号 + 时刻排序，方向写作 进/出），
  与录入格式兼容，可直接粘贴回记录区核对。

存在非配对错误（未知站点、缺票价、时间逆序、重复刷卡、参数非法）时返回
HTTP 422，错误对象与 `/api/verify` 完全一致，且不返回任何方案：

```json
{ "ok": false,
  "errors": [ { "code": "UNKNOWN_STATION", "message": "…", "location": { } } ] }
```

### `/api/fare-path-audit` 票价矩阵路径审计

无请求体。复用**已保存**的站点、票价与刷卡记录：以分区为节点、已配置的
有向票价为边，对实际行程分区对计算最低成本路径。全程只读：不修改票价矩阵、
不写入或清空账单。

返回 `200` 时的结构：

```json
{
  "ok": true,
  "trip_count": 5,
  "pair_count": 3,
  "missing": [
    {
      "from_zone": 2, "to_zone": 3,
      "reachable": true,
      "suggested_price": 7.0,
      "path": [2, 1, 3],
      "path_text": "2 → 1 → 3",
      "legs": [
        { "from_zone": 2, "to_zone": 1, "price": 3.0 },
        { "from_zone": 1, "to_zone": 3, "price": 4.0 }
      ],
      "suggest_line": "2, 3, 7.00",
      "affected": [
        { "card": "A001", "seq": 2, "entry_time": "2026-09-18 09:10:00",
          "entry_station": "中心公园", "exit_station": "大学城",
          "entry_line": 3, "exit_line": 4 }
      ],
      "trip_count": 1,
      "errors": []
    }
  ],
  "overpriced": [
    {
      "from_zone": 1, "to_zone": 3,
      "direct_price": 9.0,
      "best_price": 7.0,
      "diff": 2.0,
      "path": [1, 2, 3],
      "path_text": "1 → 2 → 3",
      "legs": [
        { "from_zone": 1, "to_zone": 2, "price": 3.0 },
        { "from_zone": 2, "to_zone": 3, "price": 4.0 }
      ],
      "affected": [ ],
      "trip_count": 1
    }
  ]
}
```

- `missing[]`：缺直达票价的分区对（按分区对稳定排序）。
  - `reachable=true`：`suggested_price` 为最低成本路径总价（建议票价），
    `path` / `path_text` / `legs` 给出完整路径与逐段单价，`suggest_line`
    为可直接粘贴回票价矩阵文本框的建议补录行；`affected` 列出受影响
    卡号、卡内序号与原始文本行号（`entry_line` / `exit_line`）。
  - `reachable=false`（不可达）：`errors` 内保留原 `MISSING_FARE`
    定位错误（逐受影响行程一条，与 `/api/verify` 完全一致），
    建议票价 / 路径 / 补录行为 `null`。
- `overpriced[]`：已有直达票价高于间接路径的分区对；`diff` 为差额
  （直达 − 间接最低，恒为正），`path` 为最低成本路径。
- 相同总价按分区序列字典序稳定选路；零价边与非对称方向按有向图语义处理；
  同区对按「至少一条边」的闭合路径计算；路径成本以整数分累加，
  等值比较不受浮点误差影响。

存在除 `MISSING_FARE` 外的数据错误（未知站点、缺出站、时间逆序、
重复刷卡、参数非法等）时返回 HTTP 422，错误对象与 `/api/verify`
完全一致，且不生成任何审计结果：

```json
{ "ok": false,
  "errors": [ { "code": "MISSING_EXIT", "message": "…", "location": { } } ] }
```

## 实现说明

- **金额精度**：业务层以元计算并保留两位小数；落库统一转整数分，避免浮点误差。
- **事务原子性**：整批替换基础数据、核验写账单均在单事务内完成；核验失败时清空
  `trip_bill`，因此任何时刻读到的账单要么是上一次完整成功的结果，要么为空。
  `/api/trial-compare`、`/api/repair-preview` 与 `/api/fare-path-audit`
  全程只执行 SELECT，不调用任何写接口，配置、矩阵、记录与账单均保持不变。
- **试算复用**：试算接口直接调用核心层 `trial_compare()`，内部对两套配置各执行一次
  `verify()`，再按 `(卡号, 卡内序号)` 对齐账单；因此配对、运营日归属、换乘抵扣与
  封顶规则与正式核验永远一致，不会出现两套口径。
- **修复搜索**：修复预览先用 `verify()` 分离出配对类错误（`MISSING_ENTRY` /
  `MISSING_EXIT`），其余错误原样返回；随后按卡分组、卡内按时间升序，用
  动态规划求最小编辑数与方案数（每条记录 keep / flip / delete，保留序列须进出
  交替），再沿最优边按稳定字典序物化前 5 个方案。各卡独立，全局最小编辑数为
  各卡之和，方案总数为各卡方案数之积，因此记录量大时也不会指数膨胀。
- **路径审计**：`fare_path_audit()` 复用 `verify()` 配对出的行程
  （`VerifyResult.trips`），除 `MISSING_FARE` 外的错误原样拦截返回。
  对每个实际行程分区对的起始分区跑一次 Dijkstra：边权为整数分（非负，
  零价边合法），堆键为 `(成本, 分区序列)`，因此相同总价按分区序列字典序
  稳定选路，且结果必为简单路径；边是有向的，非对称票价不会互相干扰。
  同区对（z→z）不允许零条边的「原地 0 元」，用「不重返起点的最短路 +
  枚举最后一条回边」求最低成本闭合路径。建议票价 = 最低成本路径总价；
  直达偏贵当且仅当 直达分 > 最低成本分（整数分精确比较，无浮点误差）。
- **数据位置**：容器内 `DB_PATH=/data/bus.db`，compose 用命名卷 `bus-data` 持久化；
  可用环境变量 `DB_PATH` 覆盖路径。
- **无外部前端依赖**：页面由 FastAPI 直接以静态文件提供，无需 npm/CDN，
  离线网络下也可使用。
